# 09 · AI 工具反思

> 对应作业工件 7。本节不做"AI 很好用"的泛泛总结，而是回答三个问题：**AI 在哪些环节真的改变了结果、在哪些环节制造了风险、我们用什么机制兜住它。**

## 1. 我们怎么用 AI

| 环节 | 用法 | 产出 | 人的介入方式 |
| --- | --- | --- | --- |
| 需求澄清 | 让模型从 SRS 中找矛盾句、列出"未给常数的要求" | RR-01～RR-10 的候选清单 | 逐条判断"是缺口还是我读漏了" |
| 架构候选 | 要求给出 2–3 个备选方案与其代价（存储、传输、门控位置） | ADR 的"备选与否决理由"列 | 用项目约束（单用户、离线、可测）否掉不适用的方案 |
| 建模 | 按 C4 / UML 生成 Mermaid 草案 | 上下文图、容器图、序列图骨架 | 逐个核对参与者与消息顺序是否与实现一致 |
| 事实核对 | 让模型在仓库里检索"阈值 / 事件名 / 表结构"并给行号 | 本文档中的常数与证据引用 | 抽查关键行号；发现不一致以代码为准 |
| 实现与测试 | 按契约生成 Java 实现与 JUnit 用例 | 领域规则、适配层、契约测试 | 只接受"能指向具体验收场景"的用例 |
| 文档 | 结构化写作、术语统一、图表语法 | 本设计工件 | 重写结论段，避免"正确但空洞" |

## 2. AI 真正改变了结果的三处

1. **把"设计原则"逼成"可断言的边界"。** 我们最初的表述是"判分不调用模型"。模型在追问下把它拆成"哪些函数必须是纯函数、`now` 怎么传、投影在哪一层剔除答案"，最终形成 `domain` 零 I/O 的分层硬约束。这不是文笔提升，而是把口号变成可测试的结构。
2. **在评审中扮演"挑刺者"。** 例如它指出："如果轮询数据库拿复习队列，到期判定会在两个地方各算一次，迟早漂移。" 这条意见直接促成"调度只在 `domain` 算一次、服务层只落库"的划分。
3. **让"备选方案"变得便宜。** ADR 里那些被否决的方案（事件溯源、全 WS、Postgres、官方 SDK）不是拍脑袋写的，而是让模型先把每个方案的代价讲清楚，再由人按项目约束裁决。**决策质量来自"看见过替代品"，而不是来自更长的文档。**

## 3. AI 制造的风险（以及我们怎么发现）

| 风险 | 具体表现 | 我们的兜底 |
| --- | --- | --- |
| **过度自信的错误设计** | 早期建议"让模型给掌握度打分，再设阈值"——听起来合理，实际直接摧毁产品承诺 | 用 ADR-01/04 把"谁能裁决"写成结构约束；任何"模型判定"提议默认否决 |
| **复杂度膨胀** | 建议引入事件溯源 + 快照 + 迁移；对一个单用户产品是灾难 | 用"MVP 边界 + 否决理由表"逐条挡回（ADR-02） |
| **局部最优** | 遇到并发问题倾向"加锁/加重试"，而不是先问"为什么会有并发写" | 要求先写"失败模式 → 结构对策"，再写代码 |
| **文档与代码漂移** | 仓库里存在陈旧注释（例如工具 schema 注释写"19 个工具"，实际 23 个；某事件注释名与实现键名不一致） | 本文档所有事实以代码行号为准；发现漂移记入风险而非照抄注释 |
| **把"看起来对"当"验证过"** | 生成看似完整的测试，但断言的是实现细节而非契约 | 硬规则：用例必须能指出它对应哪条需求/场景；`NOT RUN` 就是 `NOT RUN` |
| **提示词被当成代码** | 试图用提示词约束"不要越权"，而不是在服务端校验 | 门控下沉到调用期（ADR-03），提示词只做"引导"不做"保证" |

一个具体教训：模型很擅长**生成结构**（章节、图表骨架、字段清单），但**不擅长判断"这个约束是否已经被别处保证"**。因此我们把工作切成两半——AI 负责"展开可能性"，人负责"排除不可能"，最后用测试与证据把结论钉死。

## 4. 我们如何验证 AI 的输出

| 机制 | 做什么 | 为什么能兜住 AI |
| --- | --- | --- |
| 测试即契约 | 关键行为写成可执行用例（判分逐值、事件顺序、投影不含答案） | 幻觉无法通过断言；改坏了立刻红 |
| 不变量清单 | 把"解析不了不判错""声明不写分数""复习不推进前沿"写成硬规则 | 把"产品承诺"从文档搬到代码 |
| ADR 回签 | 每个关键决策记录背景/备选/后果，团队逐条确认 | 防止"AI 说什么就是什么" |
| 离线可复现 | 判定层不依赖模型与网络，同一输入可重复断言 | 排除"模型波动"这一不可控变量 |
| 生成质量评测 | 大纲评测输出 F1 / 有界 / 无环，可对基线回归 | 把"生成得好不好"变成数字 |
| 留痕与偏差登记 | 验证日志、失败原因、未跑项都留档 | 防止"报告成功但没跑" |

## 5. 成本

- **开发侧**：AI 的主要贡献是"把写作与样板的时间换成评审的时间"。真正的成本从"打字"转移到"读与判断"——这与传统开发的成本结构相反，因此团队必须留出评审预算，否则会用"生成速度"掩盖"判断缺失"。
- **产品侧**（与本作业相关）：判分、门槛、门控、调度零模型调用；对话回合有工具数与轮数硬上限；建议下一问走小模型并可确定性回退。**AI 在产品里是"教学能力"，不是"判定能力"**，这一定位同时决定了成本结构与信任结构。

## 6. 结论

AI 让我们更快地看到"设计空间"，但没有替我们做"设计判断"。这个项目对"如何与 AI 协作"的回答，与产品对"如何用 AI 教学"的回答是同一条：**把生成交给模型，把裁决留给可验证的规则**。前者需要人的品味，后者需要人的纪律。
